# --- Video Decode Fix (2026-08-21, 实测定位；注释更正 2026-10-08；硬件身份更正 2026-10-12) ---
# Intel 核显（Raptor Lake，DEV_A788，驱动至 32.0.101.7088 仍有此缺陷）的 D3D12 视频
# 解码器启动头几秒输出绿屏/花屏；独显 D3D12 正常（T3 对照实验实证）。
# 【硬件身份更正，缺陷 D143】原注释把独显记作 "GTX 1050 Ti"，这是错的，且错误一路扩散到
# D118 的结论里（"GTX 1050 Ti 为 Pascal，无 AV1 硬解单元"）。实测三路口径一致证明本机独显是
# **NVIDIA GeForce RTX 4070 Laptop GPU（Ada Lovelace，PCI VEN_10DE&DEV_2860，8 GB，驱动 610.62）**：
#   · nvidia-smi 报 RTX 4070 Laptop / 0x286010DE / 8188 MiB
#   · 注册表 Class\{4d36e968…}\0000 的 DriverDesc 也是 RTX 4070 Laptop
#   · chrome://gpu 的硬解清单含 "Decode av1 profile main: 128x128 to 8192x8192"
#     —— Pascal 根本没有 AV1 硬解单元，这条只可能来自 Ada
# 唯一报 "GTX 1050 Ti" 的是 WMI Win32_VideoController.Name 与 PnP DeviceDesc，其根因是
# HKLM\SYSTEM\CurrentControlSet\Enum\PCI\VEN_10DE&DEV_2860&…\4&3a9dcb36&0&0008 的
# DeviceDesc 被写成了**字面量**（正常驱动安装会是 "@nv_dispi.inf,%…%;名称" 这种间接引用），
# 即这块卡被人为改过名。该错误名称会经 DXGI_ADAPTER_DESC.Description 传进 Chromium，
# 于是 chrome://gpu 与 WebGL 的 UNMASKED_RENDERER 都显示 "GTX 1050 Ti (0x00002860)"
# ——**名字错、设备号对**。好消息是 Chromium 的 software_rendering_list / gpu_driver_bug_list
# 按 PCI vendor+device ID 匹配，不按名字，所以规避规则命中的是 Ada 的正确条目（实测已应用
# "Disable VP9 k-SVC video decoding on non-Intel GPUs"，crbug 1508379，说明确实被识别为 non-Intel）。
# ⚠ 结论：**不要再用显卡名称推断硬件能力**。任何"某卡不支持 X"的判断必须以 PCI 设备号、
# nvidia-smi 或 chrome://gpu 的能力清单为准，否则会像 D118 那样用错误前提推翻正确的实测值。
# 下面的禁用决定本身**不变**：绿屏是 Intel 核显侧实测到的，与独显型号无关。
# 禁用后回退 D3D11VideoDecoder，核显场景实测绿屏消失，硬解能力不受影响。
# 事实更正：上游该 feature 基线一直是 DISABLED_BY_DEFAULT，本仓库过去在
# media/base/media_switches.cc 把它翻成 ENABLED，再由本行抵回去 —— 二者互相抵消。
# 【155 升级期已清理 2026-10-10】apply_mcloud_source_defaults.py 不再翻转该默认
# （改为只校验 + 自愈回退历史覆盖），定制面从 7 文件降到 6 文件；本行因此不再是
# 「抵消」而是唯一且显式的禁用声明，予以保留（Intel 核显 D3D12 绿屏缺陷要求禁用）。
--disable-features=D3D12VideoDecoder

# --- Threading Optimization ---
# [第6周期修复 2026-10-12，缺陷 D170] UserBlockingAboveNormalPriority 必须与
# BrowserProcessAboveNormalPriority **成对**启用，单独启用后者净效果为零。
# 链路（M155 实证）：
#   components/performance_manager/graph/policies/process_priority_policy.cc:32-39
#     启用 BrowserProcessAboveNormalPriority 时，对 BROWSER 进程调用
#     base::Process::Current().SetPriority(kUserBlocking)；
#   base/process/process_win.cc:299-304
#     kUserBlocking 映射为 ABOVE_NORMAL_PRIORITY_CLASS **仅当**
#     kUserBlockingAboveNormalPriority 也已启用，否则仍是 NORMAL_PRIORITY_CLASS。
# 缺了这一行，上面那条"提升浏览器进程优先级"就是一条死声明：
# 安装版实测 chrome 浏览器进程 PriorityClass=Normal（2026-10-12 实测取证）。
# 附带收益（同一段代码 process_win.cc:283-289）：SetPriority 对 kUserBlocking 会把
# 该进程的 EcoQoS 置为 kUnset，即**解除 Windows 11 EcoQoS**。EcoQoS 开启时进程被
# 调度到能效核（E-core）并降频——本机 i9-14900HX 为 8P+16E，浏览器进程一旦被降级，
# UI 线程就跑在 E-core 上。因此这一条同时是**多核/混合架构**维度的修复。
# ⚠ 代价：ABOVE_NORMAL 会让浏览器进程在 CPU 争用时优先于其他应用，且解除 EcoQoS
# 会抬升功耗与发热。这是本项目"极致流畅"定位下的有意取舍；若改为续航优先，
# 需同时移除本行与下面那行（只留其一等于无效配置）。
--enable-features=UserBlockingAboveNormalPriority
--enable-features=IOThreadInteractiveThreadType
--enable-features=MojoDedicatedThread
